# compograph 布局性能改造方案

状态：已验证并实施（2026-10-22）。原提案把“热路径上的堆分配”当成主要开销，
实测证明这只对两个引擎成立，真正的瓶颈是分层排名里的二次复杂度与含容器时的
可见边表重建。方案按实测结果重排优先级，并已落地第一轮改造。

分析依据见 `docs/analysis/dynamic-dispatch.md`，基线工具见
`crates/compograph/crates/engine/cg-layout/benches/layout_cost.rs`。

## 一、验证方法

基线工具已随本次验证落地，可重复执行：

```
cargo bench -p compograph-layout --bench layout_cost
```

要点：

- **夹具用生产同型的 `GraphStore`**，形状为链加跨边（平均度约 2.2）。
  不用 `MockGraph`：改造前它的每个查询都线性扫描全边表，10k 节点下比真实
  store 慢 41 倍，测出来的是 mock 而不是布局。改造后快照只捕获一次全表，
  这个差距收敛到 1.7 倍。
- **工具不引入任何依赖**。基座自带一个计数用的全局分配器：这是唯一能同时
  看到标准库内部分配的地方，用 profiler 依赖换同样的数字并不划算。
  计数分配器的低层操作记录在 `crates/compograph/docs/archive/unsafe.md`。
- **两趟测量**：第一趟测墙钟时间，第二趟测分配次数与字节数。
- **force 固定 25 次迭代**（一个后台分块），否则 10k 节点单趟要几十秒。
- 规模 1k / 5k / 10k / 50k；另有一趟 1k–16k 的标度扫描。

### 对原提案的核对结论

| 原命题 | 结论 | 依据 |
| --- | --- | --- |
| `GraphView` 的节点与邻居查询返回 `Vec` | 成立 | `cg-graph/src/view.rs` |
| `degree` 不分配但要遍历边迭代器 | 成立，生产实现 `GraphStore` 同样是三遍扫描 | `cg-graph/src/store.rs` |
| 九个引擎都在每节点粒度查询邻居 | **不成立**：只有 breadthfirst（约 3 次/节点）与 hierarchical（约 12 次/节点）；其余七个引擎的分配数与规模无关 | 上表 |
| 一次 layout 产生数千到数万次临时 `Vec` | **部分成立**：breadthfirst 10k 节点 30 215 次，hierarchical 121 439 次 | 上表 |
| 分配是热路径的主要开销 | **不成立**：hierarchical 10k 节点耗时 3.07 s，12.1 万次分配不足 5 ms，占比不到 0.2% | 上表 |
| `Positions` 每次 layout 返回新 map | 成立，但一次新建只占十几次分配，收益可忽略 | 上表 |
| `LayoutRegistry` 与 `LayoutDriver` 持有 `Box<dyn LayoutEngine>` | 成立 | `cg-layout/src/registry.rs`、`driver.rs` |
| 用 `MockGraph` 做基线 | **不可用**：查询是全边线性扫描，10k 节点下慢 41 倍 | 基线工具的夹具对照 |
| force 在 100k 节点上跑 bench | **不可行**：斥力项是 O(N²)，10k 节点 25 次迭代已需 85 s | 上表 |
| `for_each_neighbor(&self, node, f)` 不产生分配 | **签名自相矛盾**：没有接收暂存缓冲，`&self` 下实现无法持有复用区 | `view.rs` 的索引序契约 |
| `degree` 单遍化 | 方向对但描述不准：petgraph 没有双向迭代器，只能两遍；且它统计关联边条数，`neighbors` 给的是去重邻居数 | `store.rs` |
| 引擎 enum 化收益有限 | 维持原判：每次 run 仅一次分发，实测无收益 | 上表 |

## 三、已实施的改造

### 结构快照取代逐次查询（核心）

`cg-graph` 新增 `adjacency.rs`：`AdjacencySnapshot` 一次物化节点表、边表与
三组邻接游程（出向、入向、无向）。邻接查询返回切片，既不分配也不走虚表。

- 捕获一次的成本是 O(节点数 + 边数)，查询是 O(度数)。
- `GraphStore` 的可见边表只在捕获时构建一次，不再每个查询重建。
- 邻接游程按节点索引排序且去重，与改造前的查询语义一致。

### 布局引擎改读快照

`LayoutEngine::layout` 的图参数从 `&dyn GraphView` 变为 `&AdjacencySnapshot`。
九个引擎与 `LayoutDriver` 同步迁移；`ForceSnapshot` 与 `StaticView` 随之删除，
force 后台任务直接搬快照。虚表跳转自然消失，内联恢复。

### 分层排名线性化

hierarchical 的排名原来是“逐轮剥分组”：每轮扫描全部分组找就绪集合，链式图
每轮只落一个分组，于是轮数等于分组数，整体是分组数的平方。

改为在分组图上做一次最长路径松弛（入度计数加队列），排名结果与原来逐点一致，
新增单元测试固定“深路径压过短边”的语义。16k 节点的耗时从 8.4 s 降到 21 ms。

### 中心性改读快照

`node_order` 与三个中心性函数改读快照：无向邻接表直接来自无向游程，
省掉排序与去重。

### 应用层每帧路径

新增 `StructureCache`：节点标签、节点度数与可见边表按结构版本缓存，结构不变
时跨帧复用。

- 度数由边表一趟统计得出，不再每节点调用 `degree`（含容器时那条路径是
  O(边数)，是每帧最大的开销）。
- 标签与度数的查找由线性扫描改为按节点索引的二分查找。
- 每帧不再复制标签文本与完整边表。

## 五、后续改造

剩余问题的设计与落地结果见 `compograph-allocation-followup.md`。要点：
含容器的邻接查询改为按结构惰性捕获的可见邻接索引，扁平图仍直读存储；
hierarchical 的分组、层与分组图改为扁平游程，消除每节点一个向量；
force 保留精确二次斥力，但改为按快照位置寻址并复用扁平缓冲，去掉逐对哈希查找
和迭代内分配。`Positions` 复用与引擎 enum 化经复核仍不做。

## 六、约束

- **不做向后兼容桥接**。compograph 处于开发期，无兼容负担：直接改签名，
  同步迁移 `GraphView` 的四个实现、`LayoutEngine` 的九个实现与全部调用点。
- **不写“默认实现兜底”的重复分支**，两条路径长期并存会掩盖问题并留下回归风险。
- 涉及行为变化的改动（分层排名结果、邻接顺序）补对应单元测试。
