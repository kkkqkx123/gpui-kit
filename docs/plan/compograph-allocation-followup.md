# compograph 布局性能改造后续：剩余问题设计与实施

状态：已实施（2026-10-22）。第一轮改造的实测数据与结论见
`compograph-allocation.md`，本文只处理该文第五节列出的剩余问题。

## 一、结论先行

| 剩余问题 | 判断 | 处理方式 |
| --- | --- | --- |
| 含容器时邻接查询仍是 O(边数) | 值得解决，交互路径仍在承担 | 在 `GraphStore` 内增加按结构惰性捕获的可见邻接索引 |
| force 斥力项仍是 O(N²) | 复杂度是物理模型本身，不在本轮近似化 | 保留精确逐对计算，改为按快照位置寻址的扁平数组 |
| hierarchical 每分组一个 `Vec` | 值得解决，链式图会产生每节点约五次分配 | 分组、层、分组图都改为扁平游程与单块邻接 |
| `Positions` 复用与 `layout_into` | 收益可忽略 | 不做 |
| 引擎 enum 化 | 每次 run 只有一次分发 | 不做 |

处理顺序按“收益明确且不改变可见行为”优先：先补交互路径的结构索引，
再把两个仍有明显常数开销的引擎改成扁平数据布局。两项未做项在第五节说明理由。

## 二、含容器时的邻接查询

### 问题

`GraphStore` 的扁平快速路径本来就直接读 petgraph，代价是 O(度数)。一旦存在父容器，
可见边需要把折叠子树内部的边去掉、把跨边界边的隐藏端点替换为最近的可见祖先，
原实现就在每次 `degree`、`neighbors`、`successors`、`predecessors` 调用里重建整张
可见边表。查询次数乘以边数，交互路径因此仍是 O(边数)。

布局与每帧绘制已经改读布局快照或应用层结构缓存，所以这里剩下的只有交互路径：
悬停邻域、框选、选择状态刷新。它们由用户触发，但一次邻域展开会对每个访问节点
调用一次 `neighbors`，容器图较大时仍会把整帧交互拖慢。

### 设计

在 `GraphStore` 内保存一份可见结构索引，内容就是布局快照所用的同一套物化结果：
可见节点表、可见边表和三个方向的邻接游程。邻接查询返回游程切片或切片拷贝，
不再每次重建可见边表。

- 索引按需捕获：第一次查询时从层级表计算一次可见节点与可见边，之后复用。
- 索引用引用计数包住：查询返回轻量句柄，结构变化时直接丢弃旧句柄，
  已在途的查询不会因失效而悬空。
- 结构变化才失效：节点和边的增删、端点重连、父关系变化、折叠状态变化、
  清空以及撤销恢复都会丢弃索引。标签、权重、属性、类名不改变可见结构，不失效。
- 扁平图仍走 petgraph 直读路径：没有父容器或折叠状态时不存在可见边重建，
  没有理由多一次快照。

这里刻意不采用“把暂存缓冲塞进 `&self`”或“给每个查询加一个可选外部缓冲”的方案：
前者需要内部可变状态并且调用方仍要自己判空，后者会把一次结构查询拆成两条长期
并存的路径。索引只有“已捕获 / 未捕获”一个状态，捕获逻辑只有一份。

### 语义与验证

索引由可见边表构建，邻接游程与旧查询一样按节点索引排序、去重，平行边仍计入
度数、只合并为一个邻居，自环仍只计一次。新增集成测试覆盖：父关系变化后邻接不变、
折叠后隐藏端点代理到容器且自环参与前驱与后继、撤销后恢复、增删边后立即反映。

## 三、force 的二次斥力

### 问题

斥力的定义是每对节点之间的相互作用，精确计算天然是 O(N²)。上一轮改造已经证明
耗时主要来自这项比较，而不是分配；分配只在模拟缓冲区上出现。

### 判断

不引入 Barnes–Hut 四叉树或距离截断。它们会把“精确物理模型”换成近似模型，
改变收敛路径和最终构图，需要重新调参并为视觉结果建立新的回归基线；而产品并不
承诺在该规模下使用力导向布局。应用层已经用后台分块把长任务切碎，交互不会阻塞。

因此本轮只消除逐对计算里的非必要开销，保持每次迭代的结果与改造前逐位一致：

- 坐标和偏移改为按快照节点位置索引的扁平数组，不再对每一对节点做两次坐标哈希
  查找和两次偏移哈希查找。
- 数组在模拟对象内复用，每个后台分块只从位置表装入一次、写回一次，
  迭代内部不再分配。
- 边力也按快照位置读取端点；端点不在快照中的边仍然跳过，与旧路径一致。

### 行为保持

浮点累加顺序、确定性角度、重叠快路径、温度衰减和固定节点处理都未改变。
新增“单次推进与分块推进结果完全一致”的测试，固定后台分块不改变模拟结果。

## 四、hierarchical 的每分组向量

### 问题

链式图没有强连通分量合并，每个节点自成一个分组。旧实现为每个分组建一个向量，
分组图也为每个分组建一个后继向量；随后每层再建一个向量，重心排序又为每层建
两个临时向量。耗时虽已线性，分配次数仍随节点数增长。

### 设计

- 强连通分组改为一个扁平游程结构：所有成员放在一个数组里，另一个数组记录每个
  分组的起止偏移。Tarjan 弹栈时复用一个临时向量，再追加到扁平成员表。
- 分组图改为一次收集、排序去重后的边列表，再按分组起点压成 CSR。后继遍历仍是
  连续切片，不再有每分组一个向量。
- 层同样用扁平游程表示，按排名计数后一次填充。重心排序直接在每层的切片上原地
  重排。
- 重心顺序改为按快照节点位置索引的浮点数组，未放置节点用非数哨兵表示；
  每层的打分使用一个复用的临时向量。未连接前驱或后继时的基准值仍取“已放置节点数”。
- 排名结果按节点位置返回数组，不再为每个节点建哈希表项。

### 语义与验证

分组仍按最小成员排序，组内仍按节点索引排序；排名仍是分组图上的最长路径；
层内初始顺序仍按节点索引；两趟重心排序的比较键与平局规则不变。现有关于链、
菱形、环、深路径优先、方向镜像的测试全部保留，作为行为不变的约束。

## 五、明确不做的两项

- **`Positions` 复用与 `layout_into`**：上一轮已测得一次新建只占十几次分配，
  相对一次布局的主体工作可以忽略。增加 `layout_into` 会把所有引擎的返回约定
  拆成“新表 / 写入旧表”两条路径，收益与维护成本不匹配。
- **引擎 enum 化**：每次 run 只在入口分发一次，虚表跳转不构成可测开销。
  引擎仍由注册表在运行时选择，枚举化会限制后续扩展。

## 六、验证与预期

验证以正确性为主：

- `cargo check -p compograph-graph -p compograph-layout --all-targets`
- `cargo clippy -p compograph-graph -p compograph-layout --all-targets -- -D warnings`
- `cargo test -p compograph-graph -p compograph-layout`

未重复运行完整基线工具。原因有两点：force 的 10k 节点用例在共享机器上单次就要
数十秒且波动很大；本轮改动的收益主要是分配次数与常数开销，耗时对比需要在空闲
机器上单独复测。可以确定的预期是：

- 含容器的邻接查询从“每次查询重建整张可见边表”变为“首次捕获 O(节点数 + 边数)，
  之后每次 O(度数)”。
- hierarchical 的分配从链式图每节点约五次降到与节点数无关的常数级。
- force 仍为 O(N²)，但每次迭代不再分配，逐对循环不再做哈希查找。

## 七、约束核对

- 没有为旧结构保留兼容桥接；`GraphStore` 的查询签名不变，内部缓存对调用方透明。
- 没有“默认实现兜底”的重复分支：扁平图直读与容器图读索引对应两种真实结构状态。
- 结构变化与模拟分块都补了针对性测试；未改变可见布局语义。
